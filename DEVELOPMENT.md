# Development and previews

Run `npm install` once, then `npm run dev` for the normal unseeded application (port 2500). Production `npm run build` builds only `index.html`; it does not include development preview entries or seed data.

## Local project reference evidence (Stage 1)

`engine/references.ts` adds version-1 checksummed sidecars while preserving CAD manifests and existing completion records. New revision completion markers add an optional `referenceContext` binding containing the exact context-file hash and enrollment-boundary hash; removing the entire reference extension after capture therefore cannot masquerade as legacy history. Enrollment binds the project and exact pre-feature revision manifest hashes. Those legacy revisions have no reference context. Surviving committed reference storage with a missing/invalid boundary is unavailable and is never regenerated.

Original attachments use the existing verified SHA-256 object store, outside working folders. Permanent reference/version UUIDs remain distinct from hashes; equal bytes may reuse an object without merging identities. `references/catalogs/<catalogId>.json` holds an immutable full library snapshot linked to its exact predecessor ID/file hash. New publications create an empty `references/completed/<catalogId>.<recordFileSha256>.done/` directory only after verifying the catalog and imported object. Its name binds the exact prepared bytes. There is no marker-file content write after this commit step. Publication validates unique IDs and append-only version preservation; mutable user metadata and project defaults produce a new catalog. Uncompleted snapshots are diagnostics, not published references. There is no deletion/garbage collection.

First enrollment uses the same boundary: prepare and verify `references/enrollment/<enrollmentId>.json`, then create its empty `<enrollmentId>.<recordFileSha256>.done/` directory. A failed native file creation/write/close can leave empty or truncated preparation files; without a publication directory they are incomplete diagnostics and permit fresh enrollment rather than blocking an untouched legacy project. Required enrollment cannot be recreated if a revision completion or committed library requires it. Lost acknowledgement after directory creation reconstructs the already completed publication; a fresh import always remains an explicit new identity. Existing `vault/reference-context.json` boundaries and `references/completed/<catalogId>.done.json` file markers remain readable without rewriting them. Their malformed/checksum-damaged contents remain errors, not automatically discarded incomplete attempts. Directory publications likewise reject modified records, nonempty markers, competing identities and invalid bindings.

`references/contexts/<revisionId>.json` binds the project, exact manifest-file hash, branch, parent, enrollment boundary and captured catalog ID/hash. Links distinguish inherited defaults from explicit associations and pin reference/version IDs plus optional committed component ID and historical path. Pending UI path selections resolve using the capture's validated component draft; paths/hashes never allocate identity. Capture validates the full associations and required objects before copying CAD bytes, then re-reads catalog/boundary evidence and verifies required attachment bytes before provenance and completion publication. The existing revision completion marker commits the context; orphan sidecars are never shown as saved history. Context-only captures compare semantic link signatures, ignoring component display-path changes. Unchanged associations cannot produce repeated empty revisions. Explicit associations carry forward from the actual branch baseline, including a branch origin.

Opening reconstructs metadata entirely from disk, checks all bindings/checksums and attachment existence. Full attachment hashes are checked at import, exact retrieval, linked capture and complete managed copy/adoption; opening alone does not rehash every large attachment. Unknown schemas, damaged evidence and missing content are explicit reference errors. They block reference writes/new captures and complete history-bearing copies without marking independently valid CAD manifests/objects corrupt. Recovery/export continue to use their own required CAD evidence. Review exports exclude attachments and say so in the dialog and readable summary. No absolute paths or handles are generated in reference records.

Engine tests exercise byte fidelity, distinct identities, version/context pinning, component registration/rename/branch continuity, reference-only captures, stale/invalid associations, corruption, missing content, interrupted/cancelled imports, interrupted revision completion, lost acknowledgements, legacy enrollment, copy/adoption/relocation and export exclusion. DOM tests use the actual App plus simulated native directory handles for import, default selection, context-only save, History retrieval and reopen after browser data clearing. `tests/browser/references.spec.ts` adds desktop/mobile OPFS coverage for real file-input import, component associations, version pinning and downloaded bytes. The Chrome runs were blocked at initial localhost navigation by the execution sandbox (`ERR_NETWORK_ACCESS_DENIED`), so those browser scenarios were not executed. The completed checks are Windows-host Node/DOM checks, not native browser/picker or CAD qualification. Manual Windows/macOS/Linux browser/disk testing remains required; follow the reference walkthrough in `USER_GUIDE.md`.

`references-publication.test.ts` drives `RealFileSystemAdapter` through simulated native handles and injects stream-open/write/close failures **after** `getFileHandle({create:true})` has left a file on disk. It checks first enrollment (including an existing legacy revision), subsequent imports, incomplete diagnostics, original-byte retrieval, CAD capture before retry, successful fresh import, directory creation failure/lost acknowledgement and strict handling of damaged committed evidence. It also interrupts native setup exactly after creating `references/` but before creating `references/enrollment/`: the empty parent alone is an incomplete setup diagnostic and permits either import or CAD capture to be retried first. This exception applies only when no committed revision binding requires enrollment and the parent is empty; nonempty reference storage and missing committed enrollment still block writes. These simulations do not establish native filesystem crash/durability guarantees.

## Case archival (Feature 4)

`case-lifecycle.ts` reads a small additive sequence at `vault/case-lifecycle/<branch-id>.<six-digit-sequence>.json`; no lifecycle field is added to branch publication records or historical manifests. Records bind project/branch identity and the original branch payload checksum, alternate Active/Archived, and link the preceding record checksum. Absent metadata is legacy Active; present invalid/unreadable evidence is unavailable. Do not filter `VaultState.branches`: archive filtering belongs only in the working picker/Explorer. Capture and application services guard destinations, while archived saved sources retain the existing comparison/ancestry/recovery rules.

`case-lifecycle-service.ts` uses the project writer lock, canonical baseline, connected-folder isolation, working scan and application-resolution status. Archive never changes working files or drafts; reopen is metadata-only and does not require restoring/rebinding a working folder. Writes are exclusive and read back, stale versions are rejected, and repeated current outcomes are idempotent. The full vault is copied by existing adoption/migration flows, retaining lifecycle metadata. Partial/corrupt records require inspection; there is no repair/force-clear framework or automatic cleanup.

`npm run test:ui -- tests/browser/case-lifecycle.spec.ts` runs the real App at 1366 and 390 pixels. `tests/case-lifecycle-fixture.ts` inspects only disposable origin-private fixtures; its draft setup temporarily edits/restores a known synthetic part so summary, overall and per-file drafts can be tested with an ultimately clean archived case. The browser flow fingerprints all managed-home bytes/directories outside lifecycle metadata, inspects archived history/Compare/source review, reloads and reopens. Engine tests cover identity/history preservation, dirty/unreadable cases, pending applications, archived write rejection, valid archived sources, child independence, damaged/interrupted metadata, repeated/stale requests and adoption/migration. These synthetic checks do not qualify native Windows/CAD or physical-disk atomicity.

## Case activity and divergence (Feature 5)

`src/engine/case-activity.ts` is a pure complete-project metadata projection. It reuses `getBranchBaseline`, `layoutRevisions`/`ancestryOf`, and `comparisonEndpoint`; every counted path must retain its actual validated parent edges. It never subtracts display numbers or consults Applied from records. Ownership counts and the original origin are independent from divergence; nested inherited history is not presented as a direct case save. There are no time thresholds, activity writes, folder scans or binary reads.

The existing vault head-reconstruction pass also retains **in-memory only** `branchBaselineEndpoints`: a unique saved leaf or inherited origin established before full-ancestry validation. It reuses the same leaf/fork calculation, never its damaged-head display-number fallback. Damaged committed branch evidence, competing leaves and damaged/duplicate branch publication identities cannot supply an automatic endpoint. `getBranchComparisonEndpoint` validates the endpoint and rejects unattributable damaged saved evidence. This preserves Compare's endpoint-only rules when ancestry is unavailable, without changing conservative capture/application/archive baseline validation. No disk format or historical record changes. Ordinary manual Compare is unchanged; the dialog accepts an optional explicit initial From endpoint for Settings.

Run `npm run test:ui -- tests/browser/case-activity.spec.ts` for actual-App Chrome desktop/mobile coverage. `tests/case-activity-fixture.ts` wraps the existing disposable five-file case/twenty-file Main fixture, archives a saved case during setup and observes adapter access during review. Focused engine/component tests cover ordinary and nested divergence, inherited zero-save baselines, nonconsecutive display numbers, archived cases, missing/corrupt/duplicate/cyclic/ambiguous evidence, unavailable baselines, independently healthy comparison endpoints despite ancestry damage, and real selective application/capture without merge ancestry. ## Persistent document identity

component-identity.ts owns additive, portable identity evidence. Existing project/branch identities, complete revision manifests, checksums, objects and completion formats are unchanged. New projects enroll during initialization. Legacy projects remain readable/capturable with path-only behavior until explicit enrollment.

Storage under vault/components:

- boundary.json: schema 1, project ID, timestamp, exact revision-ID/manifest-file-hash inventory at enrollment, and initial mappings for the unique saved baseline of each branch. Each distinct legacy baseline receives independent UUID registrations; equivalence is never inferred from paths/hashes. Shared exact baselines reuse one seed. The payload SHA-256 covers the entire record.
- ready.json: schema/project ID and exact boundary-file hash. Verified publication commits enrollment. A missing marker is incomplete, not legacy; explicit retry reuses the exact valid boundary. Malformed or already-published evidence is never overwritten.
- revisions/<revision-id>.json: schema/project/revision/branch IDs, exact manifest-file SHA-256, boundary checksum, parent identity checksum, complete one-to-one path/component-ID mapping, confirmed rename pairs, replacement paths and safe application transfers. A payload checksum covers all fields. This is written and read back before the existing revision completion marker. Only a matching committed revision exposes its mapping; orphan sidecars remain incomplete diagnostics.

Read reconstruction validates project/manifest/parent binding, complete coverage, unique paths and IDs per revision, inherited continuity, one-to-one rename decisions and newly allocated identities against established registrations. Application transfers must reference verified captured operation provenance and a matching source mapping. Unsupported schemas and missing/conflicting/damaged evidence produce unavailable component state and block identity-sensitive writes; path history, snapshot comparison and ordinary fresh recovery retain their existing evidence rules. A present components file instead of directory is damage. Complete erasure of all component evidence is indistinguishable from legacy absence.

Lifecycle: scans allocate no authoritative IDs. The UI keeps branch/project-scoped review decisions only in its session draft. Capture reloads under the existing writer lock, scans again, checks the project/branch/baseline manifest/boundary/changes signature and validates missing-old/new-target associations. Provisional UUIDs are allocated for that attempt and become authoritative only with verified completion. Failed uncompleted attempts can allocate fresh provisional UUIDs on retry; they never expose two published registrations. A completed revision survives lost acknowledgement and reconstructs its published mapping on reopen. No IndexedDB identity authority, global latest-filename index or second transaction framework is introduced.

The deliberate migration is prospective. Existing manifests/bytes are never rewritten. Only enrollment baselines receive mappings; earlier revisions keep path history. Distinct older baselines are not equated. A branch originating from an older unregistered revision establishes IDs at its next capture, and old-ID reappearance association is not supported. New branches from identity-bearing revisions inherit their source mapping without an automatic revision.

Complete managed project imports are recognized before ordinary CAD import and routed through the existing verified adoption pipeline. Imported project/publication/branch-location bindings are validated, paths must stay within independent working leaves, and duplicate project registrations in the destination workspace are rejected. Vault copies include all component records and are byte-verified; whole workspace migration refuses unavailable component evidence. Relocation uses relative management records. Classification/permission failures may occur before allocating a destination. Duplicate copies are discoverable only within authorized connected locations; no global copy registry or multi-device lock is claimed.

Application safety is additive to the existing three-way planner and is recomputed during preparation/execution: shared IDs at different endpoint paths and distinct IDs at a shared path block affected source writes. Legacy/unavailable identity endpoints block affected actions when tracking is enabled. Unselected safe paths remain usable. New source-file additions retain their identity through explicit application transfer evidence bound to the captured operation; unrelated working additions remain new components. This is not a rename-aware integration planner. Existing provenance, recovery and single-parent history stay intact.

Compatibility: use this or a newer compatible build after enrollment. Older builds can still read historical manifest formats but do not enforce identity continuity; any post-boundary completion without a sidecar is reported unavailable when reopening here. Same-origin locks do not coordinate sync clients or other machines. Synthetic filesystem and Chrome OPFS tests make no native SolidWorks/reference/rebuild qualification claim.


## Cross-platform folder addresses and browser access

Production consumers use `utils/folder-path.ts`. `parseAbsoluteFolderPath` determines Windows drive/UNC versus POSIX syntax from the root text; `composeFilePaths` validates managed relative descendants separately with the existing validator. POSIX roots are not passed through Windows device-name rules. Case, Unicode spelling and literal POSIX backslashes are retained, with no tilde/environment expansion. Ambiguous double-leading POSIX slashes and empty/traversal segments are rejected. Windows roots keep their normalization and filename checks. The old `windows-path.ts` exports remain compatibility aliases. Portable relative validation, collision checks, component IDs and immutable records are unchanged.

FolderAddressDialog supplies required home setup plus neutral location settings and Windows/Finder/Linux instructions. All production pickers call `utils/folder-access.ts` for capability, secure-context and top-level checks. Remembered home reconnection is checked too. Denied/revoked access is actionable; home cancellation retains the empty-folder guidance and project cancellation keeps the import dialog usable. OS/user-agent strings never select path syntax.

Local preferences retain the existing `windows-root:` and `windows-handle:` keys without an IndexedDB or portable metadata migration. Neutral save/get APIs also accept POSIX text; old API names remain aliases. A supplied real handle must match the saved handle, or a matching original remembered home/workspace binding for a legacy unbound setting. An unproven legacy address is retained but requires confirmation. Imported/relocated copies cannot adopt an old path by portable ID alone. Session state also checks the access-root object. Failed handle cloning aborts the entire preference transaction, with session-only fallback. An OS move retaining the same handle cannot reveal its new absolute path; the user must edit the address explicitly.

Focused tests: `folder-path.test.ts`, `folder-preferences.test.ts`, `folder-platform.test.tsx`, existing home/setup/path suites, and `tests/browser/folder-platform.spec.ts`. The test-only native-handle facade supplies structured cloning for known test handles, reflecting browser handle cloning without allowing arbitrary functions to clone. Browser checks use actual Chrome OPFS/IndexedDB with substituted pickers for Windows/UNC/macOS/Linux address strings, create/capture/branch/confirmed rename/recovery/reopen and shortcut paths. See the real-device checklist in USER_GUIDE.md. Actual host: Windows; POSIX input tests are simulations, not native macOS/Linux qualification.

API background: [Chrome File System Access](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access), [showDirectoryPicker security and availability](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker). No fallback silently substitutes a read-only directory upload or origin-private storage for the user's selected local storage.

## Export revision for review

`engine/review-export.ts` builds a pure preview from the selected committed manifest, its recorded branch, global display number and available component evidence. Execution reloads under the existing project lock and rejects a changed/forged preview. It uses the existing working-folder binding/isolation safeguards, object-store verification, recovery parent-directory helper, bounded file streams and verified inventory reader. It never reads working-file bytes or writes project metadata.

The first output child is `<sanitized-project>_<sanitized-recorded-branch>_R<number>` (at least two revision digits). Existing case-insensitive folder labels produce an explicitly previewed `-2`, `-3` etc. alternative; execution never silently substitutes a name. The child is created exclusively with the existing adapter safeguards. A selected parent may be a common ancestor only when the proposed child is separate from all protected vault/working locations. All required saved objects are verified before child creation.

Complete exports preserve original paths and empty directories. Selected exports preserve paths by default; the opt-in standalone naming option sanitizes the stem and adds the recorded branch/revision before the original extension. Mapping, directory/file prefix and case-folded collisions are rejected; no colliding file is omitted. Nonportable preserved paths are rejected rather than renamed. Summary/temporary-marker name conflicts get explicit numbered metadata names in the preview, retaining any snapshot files that use the usual metadata names.

`_CADTREE_REVIEW.txt` is ordinary readable output, not a new vault format. It contains saved context and notes, mappings, hashes and available component IDs; no configured address, filesystem handle or generated absolute location is included. Missing legacy identity evidence is labelled unavailable without regeneration. `_CADTREE_EXPORT_INCOMPLETE.txt` is retained on failure/cancellation where possible and removed only after exact output inventory/hash verification. Any failed attempt identifies its proposed child in the caller error; retry uses a fresh previewed child. No export registry/database or network delivery is added.

`ReviewExportDialog.tsx` uses existing modal/notice/progress patterns. The History action operates on the inspected saved revision; App executes it as a cancellable operation without refreshing working files, switching branches or changing the inspection selection. The dialog previews output names and the readable summary before confirmation and keeps failed output details visible while proposing a fresh retry.

Checks: `review-export.test.ts` covers saved-versus-working bytes, binary fidelity, global branch/revision labels, confirmed rename history/IDs, full empty-directory structure, partial selection, sanitized collisions, reserved summary/marker names, existing and protected destinations, corrupt/missing objects, stale previews, cancellation, write/verification failures and retry. `components/review-export.test.tsx` runs the actual App with simulated native folder handles and confirms a saved Alternative export leaves Main active and the entire source home unchanged; dialog tests cover opt-in naming and failed/cancelled fresh retry. These Windows-host Node/DOM tests do not qualify native CAD dependency repair or OS picker behaviour.

Manual walkthrough:
1. Save two revisions of a disposable CAD project. Leave a newer working edit unsaved as a revision. In History inspect the older snapshot and choose **Export for review**.
2. Keep **Complete project**, choose an external parent, inspect `<project>_<recorded-branch>_R<number>` and the proposed file list, then export. Check old saved bytes, original filenames, nested/empty directories and the readable summary.
3. Inspect a saved revision from a different branch while leaving the current branch active. Export one selected file with labels off, then repeat with **Add branch and revision to filenames** on. Confirm extension, branch label, global number, partial notice and original-to-exported mapping. Inspect a renamed component before/after its confirmed rename and check historical filenames and IDs.
4. Repeat under the same destination parent: confirm the numbered proposal and unchanged existing copy. Cancel during a larger export or deny destination access; verify incomplete output is identified, no success appears and a fresh retry succeeds.
5. Reopen the original project: active working context, current working bytes, revision/branch count, component IDs and immutable metadata must be unchanged. Open exported standalone/native files separately and repair any references manually as needed; automatic dependency discovery and format conversion are outside this feature.
